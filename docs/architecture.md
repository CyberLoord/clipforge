# Устройство

Один Go-бинарник запускается с разными ролями. В Compose это пять процессов: HTTP API, dispatcher, анализ, рендер и обработка событий. React раздаётся API как статические файлы. PostgreSQL хранит состояние заданий и outbox, Kafka доставляет сообщения между ролями. Исходники и результаты лежат в общем каталоге данных. Для разработки роль `all` запускает те же обработчики в одном процессе; Kafka всё равно требуется.

## Этапы

`probe → transcribe → select → render → completed`

В режимах `split` и `montage`: `probe → select → render → completed`. Аудио не извлекается, субтитры не добавляются. Режим хранится в задании; воркер выбирает провайдера для каждого задания отдельно.

После этапа воркер сохраняет результат и следующий этап в PostgreSQL. Повтор после ошибки использует уже сохранённые данные. Для повторного экспорта меняются границы и ревизия одного клипа, очищается его ссылка на файл; остальные клипы остаются доступными.

Новая нарезка завершённого или остановленного задания сбрасывает результаты и запускает `probe` с тем же исходником. Можно сменить режим без повторной загрузки. Старые завершённые файлы остаются в каталоге данных, но больше не выдаются через API.

Загрузка потоковая. Сначала проверяются расширение, сигнатура контейнера и размер, затем файл атомарно переименовывается и создаётся задание. ffprobe асинхронно проверяет дорожки, длительность и разрешение. HTTP-запрос не ждёт обработки видео.

## Доставка и восстановление

API сохраняет задание в PostgreSQL. SQL-триггер в той же транзакции записывает команду и событие в outbox. Dispatcher публикует их в Kafka с ключом `job_id` и удаляет строки после подтверждения брокера. Публикация и коммит PostgreSQL не атомарны: сбой между ними приводит к повторной доставке.

`clipforge.analysis.v1` обслуживает этапы `probe`, `transcribe` и `select`. Когда план готов, анализ сохраняет его и ставит команду в `clipforge.render.v1` через outbox. Рендер выполняется другой consumer group и масштабируется отдельно. В сообщениях нет видео, аудио и расшифровок — воркер получает данные задания из БД и читает общий каталог.

Команда содержит поколение запуска и этап. Получение задания проверяет их вместе со статусом `queued`, временем доступности и лимитом попыток. Старая или повторная команда не создаёт вторую попытку. Каждая полученная попытка получает случайный токен и срок аренды. Heartbeat продлевает аренду; записи результата проверяют токен, статус и срок. Потеря аренды отменяет context.

Kafka offset фиксируется после успешного обработчика: сохранённого результата, передачи в рендер, записи ошибки или распознавания устаревшей команды. Ошибка БД не подтверждает сообщение. Dispatcher отдельно возвращает просроченные аренды в очередь с новым поколением либо завершает задание, если исчерпан лимит. Для ожидающего задания без pending-команды в outbox dispatcher повторно публикует ту же команду, если с её доставки прошло 15 минут. Это восстанавливает доставку после долгого простоя consumer и истечения retention. Dispatcher не выполняет обработку видео и не подменяет Kafka SQL-очередью.

Временные сетевые ошибки, 429, 5xx и таймауты повторяются с задержкой. Следующая команда лежит в outbox до `available_at`; ожидание не блокирует Kafka partition. Ошибки входных данных, невалидные ответы модели и ошибки FFmpeg завершают задание. Терминальный сбой также попадает в `clipforge.dlq.v1`. Пользователь может запустить новую попытку через API.

Сбой после вызова провайдера, но до сохранения результата может повторить платный запрос. Exactly-once для обработки видео не гарантируется. Уникальные пути файлов и проверка токена не позволяют старой попытке подменить опубликованный результат.

Отмена фиксируется сразу, процесс останавливается при следующем heartbeat, по умолчанию примерно в течение 10 секунд при доступной БД. При SIGTERM процесс завершает HTTP-запросы и отменяет обработчики. Незаконченные задания восстанавливаются после истечения аренды; оборванные попытки учитываются в лимите.

## История событий

`clipforge.events.v1` содержит переходы статуса и этапа, включая повторные попытки. Отдельная группа `clipforge-history` сохраняет события в `job_events`. Ключ события и последовательность внутри задания защищают проекцию от дублей. API отдаёт последние 100 событий по порядку; интерфейс показывает время, этап, номер попытки и ошибку. Проекция может отставать от текущего состояния задания.

Группа `clipforge-failures` сохраняет DLQ в таблицу `dead_letters` для диагностики. Перечитывание событий восстанавливает историю в пределах Kafka retention и не запускает обработку видео. Топики, группы и команды для проверки описаны в [Kafka](kafka.md).

## Медиа и AI

Для монтажа FFmpeg выбирает до 48 кадров по всей длительности. JPEG ограничены 640 пикселями по большей стороне и 256 КиБ на кадр; временные метки берутся из декодированных кадров. Модель получает кадры и возвращает два или три плана монтажа с различающимися выбором, порядком или длиной сцен. Go проверяет границы, пересечения, общую длительность и повторяющиеся планы. Модель не получает непрерывный видеопоток: короткое событие между кадрами может быть пропущено, особенно в длинном исходнике.

Планы сохраняются в JSONB `clips` перед экспортом. Каждый отрывок нормализуется отдельно, затем части соединяются в указанном порядке. Повтор этапа `render` использует сохранённый план и не вызывает модель. Временные части находятся в каталоге с токеном аренды; чужой воркер их не удаляет.

FFmpeg запускается через `exec.CommandContext` с отдельными аргументами. Вход ограничен локальными MP4, stderr ограничен 8 КиБ. Выход: H.264, yuv420p, faststart, 540×960; звук при наличии аудиодорожки — AAC. Исходное изображение вписывается в тёмный фон. В контейнере установлены libass и DejaVu Sans для русских субтитров.

Аудио извлекается в mono MP3, 16 кГц, 32 кбит/с. Распознавание и выбор фрагментов имеют разные интерфейсы. OpenAI возвращает сегменты с временными метками и структурированный список клипов; Go проверяет границы, длительность, число фрагментов и пересечения более половины меньшего интервала.

Распознавание использует сегментные временные метки. Для длинного сегмента время между группами слов распределяется приблизительно; покадровой синхронизации каждого слова нет. Группы субтитров обрезаются по интервалу клипа.

Документация провайдера: [изображения](https://developers.openai.com/api/docs/guides/images-vision), [GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [speech-to-text](https://developers.openai.com/api/docs/guides/speech-to-text), [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat).

## Ограничения

- Один пользователь, без авторизации. Compose публикует порт только на `127.0.0.1`; для общего доступа нужны аутентификация и ограничения запросов.
- Локальная файловая система. Все роли в Compose используют один volume на одном Docker-хосте. Для нескольких машин потребуется общее или объектное хранилище. `WORKERS` ограничивает параллелизм анализа, `RENDER_WORKERS` — рендера; число partitions ограничивает активных consumers в группе.
- Compose содержит один Kafka broker/controller с replication factor 1. Это локальная конфигурация без отказоустойчивости, TLS и SASL. Порты API и внешнего Kafka listener опубликованы только на `127.0.0.1`.
- Dispatcher публикует ограниченные пачки outbox под PostgreSQL advisory lock. Это последовательная точка доставки, не рассчитанная на большой поток сообщений. Kafka retention не удаляет строки истории из PostgreSQL.
- История показывает последние 100 заданий. Политики удаления исходников и завершённых заданий пока нет. Нужно следить за свободным местом. При потере ответа на INSERT исходник сохраняется: неизвестный результат записи в БД не должен оставить возможное задание без видео; такой сбой может оставить лишний исходник.
- Одна основная аудиодорожка, без отслеживания лица и умного кадрирования. Видео короче 15 секунд, длиннее настроенного лимита или с разрешением выше 8K не принимается.
- Выбор моментов зависит от модели. `montage` анализирует изображения, `openai` — речь. Режим `split` делит видео по времени; `demo` использует заранее подготовленный текст.
- Монтаж использует прямые склейки и звук выбранных сцен. Нет музыки, привязки к биту, изменения скорости и переходов. Речевой контекст в режиме `montage` не анализируется.
- Клиент OpenAI проверяется на тестовом HTTP-сервере. Реальные запросы требуют пользовательского ключа и отдельной проверки качества на своём материале.
